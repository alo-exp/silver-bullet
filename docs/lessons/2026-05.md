# Lessons Learned — 2026-05

## practice:testing

2026-05-07 — When the same behavior must be proven in multiple runtimes, keep one scenario suite and swap only the runtime adapter. Duplicating scenario bodies creates drift and makes failures harder to compare. Serialize runs if both runtimes touch shared state.

## practice:packaging

2026-05-07 — When a target runtime lacks a native plugin package, ship a thin wrapper that fetches the authoritative upstream content at install time. The wrapper should be registry-only, not a second copy of the real plugin.

## devops:automation

2026-05-07 — Schedule-based automations are predictable but cost proportional to invocation count. If an event-driven trigger exists, prefer it for issue triage or alerting; otherwise bridge with the source system (for example via webhook or CI) instead of polling more often than needed.

## practice:release

2026-05-07 — Multi-runtime releases should treat each supported runtime as a first-class release target. The release gate should verify every runtime path you ship, not just the primary one.
