# Enforcement Architecture

Silver Bullet enforces workflow compliance through twelve independent layers. No single layer can be bypassed in isolation — they compose to provide defense-in-depth. The same twelve layers appear in the README and in `silver-bullet.md` §1; [HOOKS.md](HOOKS.md) lists every registered hook, including the gates beside these layers.

**Security model.** Silver Bullet is an enforcement aid against a confused, over-eager or mistaken agent, not a sandbox against a malicious agent with arbitrary code execution as the same user.

## The 12 Layers

Uses active `.planning/workflows/<id>.md` admission first, then skill markers when no composed workflow is active |

## Planning-Floor Gate

`dev-cycle-check.sh` enforces pre-execution readiness. When an active `.planning/workflows/<id>.md` exists, the gate admits non-trivial source edits for that workflow: the active workflow is the only workflow file, the id persisted in `${SB_RUNTIME_STATE_DIR}/active-workflow`, or `SB_WORKFLOW_ID` (an override that only a hook-visible environment can set; a first-line `export SB_WORKFLOW_ID=…` in a Bash command also selects among several workflows). The skill-based check is the legacy fallback for projects without a composed workflow. The gate enforces nothing outside a Silver Bullet project, judges every write target (file tools, `NotebookEdit`, MCP file writes, apply_patch paths and shell writes) in canonical form, treats `lib/` symlinked to `src/` as source, and does not gate `tools/src-gen.py` or test layouts (`src/test/`, `*_test.go`, `test_*.py`). A cumulative budget of 300 characters per session covers tiny typo edits. The gate does not try to predict which files a shell command writes (that question has no end: globs, `cd "$(…)"`, patches, interpreters, copies of the recorder). It verifies, at every decision point, that the artifacts the gates rest on are what the sanctioned writers last recorded (`hooks/lib/integrity.sh`).

**Invariant I (integrity).** A gate trusts an artifact only while its content matches the keyed record (HMAC-SHA256 with the per-install key over the project root, a monotonic counter and the branch). The rule has three states. *Verified*: the record is authentic and each artifact either matches it or is named as diverged. *Unbaselined*: the install is live (it has made its key) and the project has no record, no counter and no sealed state. Nothing proves the live files, so the gate is strict: planning floor unsatisfied, the template's required lists, no trivial bypass, the skill state counted as empty, and the message says to restart the session (session start records the project) or run `/sb:init`. A new worktree or a fresh clone of an adopted branch is a project as soon as it holds both contract files, and is unbaselined (strict) until its first session start records it; a project created inside another baselined root is unbaselined until then as well. *Untrusted*: a record, counter or seal that is deleted, rolled back, forged, unkeyed where a key exists, symlinked or from another branch. It gets the same strict treatment, names the cause and logs the event to `seal-events.log`. On a mismatch the gate falls back to the strict default (the required lists last recorded or the template defaults, trivial bypass off), names the diverged artifact and the one-step recovery, and removes an unblessed trivial marker. The only state that reads the files as written is an install that has never made its key (a fresh sandbox, or an install that has not yet had a session): there is nothing to compare, so nothing is claimed. The key is made by the first session start, `record-skill.sh` or baseline.

The artifact set is closed: the skill state (sealed lines only: `<state>.seal`), the legacy trivial marker (must be absent unless blessed; a trivial path named in the config is never honoured), `.silver-bullet.json` (the whole canonical config, minus the keys the hooks keep up to date themselves: `recommended_tools` and `sb_enforcement_tier`; it is recorded as text, so formatting does not count), `silver-bullet.md`, `.silver-bullet.prompt.json`, `CLAUDE.md` / `AGENTS.md` and `.planning/{ROADMAP,STATE,PROJECT}.md`, one record per project root in `${SB_RUNTIME_STATE_DIR}/integrity-<n>.rec`. File digests are SHA-256 (one openssl process; python3's hashlib, then POSIX cksum only where neither exists) and the record is an HMAC-SHA256 over the whole body, the project root, a monotonic counter and the branch. **The project root** of a directory (a directory that does not exist yet is judged by its nearest existing ancestor; both the resolved and the logical spelling of the path are walked) is the nearest directory at or above it that is a *baselined root*. Every baselined root has **three anchors**, of two kinds. Two name its PATH: (a) its line in `${SB_RUNTIME_STATE_DIR}/baselined-roots` (the real path, a TAB and the identity) and (c) a marker file `root-<CRC of the real path>` in the state directory (content: path and identity; the stored path must equal the path asked about, so a CRC collision gives no false anchor and never displaces another path's marker). One names its IDENTITY: (b) the integrity record named by the identity. The path anchors keep a path strict whatever now stands there; either one is enough. The record follows a renamed or moved directory but cannot hold a replaced one: a copy put at the old path has a NEW identity, so after a swap only the registry line and the marker hold the path. A root's **identity** is `device:inode:birth-time` of its directory (GNU `stat %d:%i:%W`, BSD `stat -f %d:%i:%B`); a rename or move keeps it, and a new directory created in a deleted one's place does not. The record is bound to the identity in its keyed digest, so a renamed project keeps it. The registry and the markers are not signed (they only ever add strictness). They are protected by the **state-tamper guard** of `dev-cycle-check.sh` (`sb_pf_state_violation`), which covers every file of the state directory (the registry, its lock, the markers, the records, the key, the skill state) for file tools and for shell writes, and is the reason a registry or marker cannot be removed by an ordinary command (`STATE TAMPER BLOCKED`); the hooks write these files outside the agent's tool path. What it refuses: `rm`, `mv`, `cp` or `install` over them, a redirect, `truncate`, `tee`, `sed -i`, `find -delete`, `dd`, `ln` and the file tools (Edit, Write, MultiEdit, NotebookEdit, `apply_patch`), also after a `cd`, `pushd` or `git -C` into the state directory, and a deletion of a directory above it (`rm -rf`, `git clean`). Four sentinels (`session-init`, `stack-compression-mutex`, `sb-friction-log.md`, `roadmap-edit-override`) stay open to a plain write (a redirect, `tee`, `touch`, `truncate`, `rm`, a file tool) and only while the name is a plain file with one link, a directory, or absent: a hard link or a symlink under a sentinel name, a copy, move, link or install onto it is refused, and so is a hard link (`ln` without `-s`, `link`, `cp -l`) made FROM a state file to anywhere (writing through the new name would write the state file). `git clean` (without a dry run) is refused when the work tree it cleans (the working directory, `git -C`, `--work-tree`, `GIT_WORK_TREE`) is the state directory, a directory above it or not known; `git reset`, `stash`, `checkout`, `restore` and `rm` are refused inside it. A `cd` is followed as `bash` runs it (logical `-L`, physical `-P`); one that may not take effect (the right side of `&&` or `||` when the next command is judged, the body of an `if`, `while`, `for` or `case`, a target that is no directory when the command is judged and that no earlier `mkdir` made) leaves the directory before it as well as the one after it, and a relative write is judged in each. A `cd` whose effect cannot be read before the command runs (a target computed at run time, `CDPATH`, `cdable_vars`, an assigned `HOME`, `OLDPWD` or `PWD`, a function that changes directory, `pushd -n` or a rotation, `find -execdir`) makes the directory dynamic: a relative write there is then judged by its NAME (an entry of the state directory, a contract file, or a glob that can match one) and refused when it is protected, and an ordinary name is allowed. **Remaining limits** (lexical, not prevented): a protected path assembled at run time and written by an absolute name (`rm "$d/baselined-roots"` with `d` read from a file), an interpreter one-liner or script whose text the analysis does not read (`python3 -c`, a script file, a sourced file that changes directory), a hard link made earlier by such a means (a link that already exists under a sentinel name is refused when a tool writes through it, not detected when it is made), and, under a dynamic directory, a name the analysis cannot read (`rm "$f"`) or a glob that cannot match a protected name by pattern. A root is registered when it is baselined (a session start also refreshes the lines after a rename). A registered path anchors BOTH by identity AND by path: the identity follows a renamed or moved root, and the path stays strict for as long as one of its path anchors exists, whatever now stands there (a copy put in its place, a symlink, a directory recreated after `rm -rf`, with or without the record). Anchors are removed only by an honest committed-removal retirement of the matching root, by the user's Recovery recipe below, by the twin rule (a fresh session drops the old-name line and marker of a renamed root whose old path is gone and whose identity is live under another), or, for registry lines only, by the 200-line cap (oldest first; the markers and the record of the root remain). A registered root with a missing record is unbaselined (strict), never inert. No git is read to decide it, and a subdirectory project (a monorepo `app/`) is a root of its own. A directory that was never baselined is judged by its files alone: the nearest directory holding both contract files, stopping at a git root. A stray `docs/silver-bullet.md`, a vendored `.silver-bullet.json` or a repository that never had Silver Bullet is no project. **Accepted consequence**: a deleted root's path, or a reused `device:inode` on a filesystem without birth time, can make an unrelated repository at that path report `PROJECT NOT BASELINED` until the user runs the Recovery recipe; the gate message says so and points here.

**Write targets are judged under both spellings.** Every file-tool path (Edit, Write, MultiEdit, NotebookEdit, apply_patch paths, MCP file writes) and every shell write target (redirects, `tee`, `cp`, `mv`, ... through the shell analysis) is judged as its RESOLVED path (symlinks followed) and as its LOGICAL path (joined to the payload's `cwd`, else the process's working directory, with `.` and `..` collapsed lexically and symlinks left alone); either one under a root or a protected artifact is judged. A source folder symlinked outside the project (`mv src X && ln -s X src`) is therefore still the project's source by name, from the project folder, from its parent, with a payload `cwd` that differs from the process's, and through `..` detours. A symlink that points INTO a project from an unrelated place is judged by where it lands, as before. The shell analysis starts from the payload's `cwd` (the host runs the command there, wherever the hook process is; Codex's `workdir` is joined to it) and keeps BOTH spellings of the working directory through `cd`, `pushd`, `popd` and `cd -`: the logical one joins lexically as `bash -L` does (`cd .` and `cd sub && ... ../x` stay under the symlink's name; `cd -P` resolves), the resolved one is where the kernel puts the shell. A `cd` to a target the analysis cannot read (`cd "$(cat f)"`, `popd` with a stack it does not model) makes later relative writes dynamic.

**Recovery** (the gate messages point here; none of it is for the agent): with the files back (restore them from HEAD, or re-run `/sb:init`) a new session records the root again. For an intentional uninstall that a restart cannot retire (the record is gone, or the root is not a git repository, so no committed removal can be shown), or for an unrelated repository held at a retired root's path, the user, from a terminal outside the agent, takes the root out of all three anchors and starts a new session. The identity is `device:inode:birth-time` (GNU `stat -c %d:%i:%W`, BSD/macOS `stat -f %d:%i:%B`); on a filesystem without birth time that prints a trailing `:0`, which is dropped. Set `ROOT` to the project directory (a symlink or a trailing slash is normalised) and `SD` to the state directory, then paste this (it defines a function and calls it; it never exits your shell, and it refuses an empty or non-existing ROOT; tested verbatim with GNU stat and, through a stub, BSD stat):

```sb-recovery
sb_recover() {
  local ID N m mp mi ROOT_IN="$ROOT"
  [ -n "$ROOT_IN" ] && [ -d "$ROOT_IN" ] || { echo "ROOT is not an existing directory: $ROOT_IN" >&2; return 1; }
  ROOT=$(cd -P -- "$ROOT_IN" && pwd -P) || return 1
  ID=$(stat -c %d:%i:%W "$ROOT" 2>/dev/null || stat -f %d:%i:%B "$ROOT")
  ID=${ID%:0}
  [ -n "$ID" ] || { echo "cannot read the identity of $ROOT" >&2; return 1; }
  N=$(printf '%s' "$ID" | cksum | cut -d' ' -f1)
  ROOT="$ROOT" ID="$ID" awk -F'\t' '$1 != ENVIRON["ROOT"] && $2 != ENVIRON["ID"]' "$SD/baselined-roots" >"$SD/baselined-roots.new" && mv "$SD/baselined-roots.new" "$SD/baselined-roots"
  for m in "$SD"/root-*; do
    [ -f "$m" ] || continue
    IFS=$(printf '\t') read -r mp mi <"$m"
    if [ "$mp" = "$ROOT" ] || [ "$mi" = "$ID" ]; then rm -f "$m"; fi
  done
  rm -f "$SD/integrity-$N.rec" "$SD/integrity-$N.rec.hwm"
}
sb_recover
```

A nested project written beneath a baselined root (two file writes) is not a new root: it inherits the root's record until a session start baselines it. **Every gate decision reads the verified record**: `sb_integrity_gate` resolves and verifies the project, `sb_iv_jq` queries the recorded config (the template's strict defaults while the project is unbaselined or untrusted), `sb_integrity_state_contents` reads the state, `sb_integrity_trivial_ok` the marker. What counts as source (`src_pattern`, exclusions), the release switches, the lists, the state path and every other key come from the record, so a changed file cannot take anything out of the floor, and any drift of a contract file stops final delivery (`gh pr create/merge`, `gh release create`, deploy). The record is re-hashed at every decision, within one process only the first decision verifies: a cross-process cache keyed on (mtime, size, inode) was rejected because an interpreter can change a file and restore its modification time, so the stat triple cannot vouch for the protected set. docs/PROTECTED-READS.md is the machine-generated audit of every place that reads a protected value; `tests/hooks/test-integrity-audit.sh` fails when a gate reads one outside the record.

The sanctioned writers keep the record in step: `session-start` (a fresh session is the trust anchor and records everything as it is, after removing any trivial marker; a first baseline that differs from what git has committed is shown to the user and logged, as is a re-baseline over a divergence), `record-skill.sh` (the state seal; and, when a contract-writing skill is recorded (`sb:init`, `sb:update`, `sb:migrate` for all of the contract files, `sb:add` and `sb:devops` for declared config keys only), an `unlock` entry in the signed record for two hours, `hooks/lib/contract-unlock.sh`), the file tools (a file-tool write of an artifact is vouched for by the gates that allowed it) and the hooks that edit the config themselves. **A contract-writing skill adopts only what it is declared to write.** It gets no unlock at all when a contract file already differs from the record when it starts (a drift that predates it is never laundered: it is logged as "got no unlock" and only a session start, which is the user, adopts it); while its unlock runs, only its declared files and, for `sb:add` (`_github_project`, `issue_tracker*`) and `sb:devops` (`project.active_workflow`), only its declared keys are expected and adopted; any other key stays a drift and the recorded values keep applying. A change made any other way (`cp`, `sed`, an interpreter, a patch, a dynamic `cd`, a copied recorder) diverges from the record whatever the spelling: a changed `.silver-bullet.json`, `silver-bullet.md` or prompt file stops source edits and final delivery with `ENFORCEMENT CONTRACT CHANGED`, a message addressed to the user (review the change with git, revert it, or restart the session so session start records it; the agent is told not to try to re-record it), a changed instruction or planning file is reported and recorded at the next file-tool write or session start, an unblessed trivial marker is deleted, and state lines nobody sealed count for nothing. Deleting or moving the config or `silver-bullet.md` does not switch the gates off, and neither does deleting the record, its counter or the state seal: without a record the project is unbaselined, which is strict. A Stop with a deleted or emptied state is judged by the keyed record, not by the counter file: once the recorder has tracked a skill in a project the record says so (`tracked`), and an empty state then gets the planning floor; only a project the record says never tracked anything (and that is not unbaselined or untrusted) ends quietly. A removal of Silver Bullet is retired by a fresh session (startup or clear, never compact or resume) only when the root is registered, its record verifies, both contract files are absent from the working tree and `git --no-replace-objects` shows that HEAD (a real commit, not an unborn orphan) tracks neither. Nothing else is consulted: not `origin/HEAD`, `main` or `master`. An uncommitted removal keeps the record, and the message says to restore the files from HEAD (`git checkout HEAD -- ...`) or commit the removal and start a new session; it never suggests removing Silver Bullet from a shared branch. Retirement also drops the root from the registry, so a reinstall baselines it afresh. In an unbaselined project only a session restart helps (`/sb:init` cannot unlock it, because the unlock needs a record).

`patch`, `git apply` and `git am` are tree writes: they need the planning floor like any source write (a readable diff file names its paths, so a docs-only patch does not). No diff is parsed; what a patch does to a protected artifact is caught by the record.

**What is not prevented (residual).** Identity is `device:inode` only where the filesystem reports no birth time: there an inode reused by a new directory looks like the old root. On platforms with a birth time (one-second resolution) the residual is a new directory created within the same second as the ORIGINAL root's birth that also reuses its inode. A project copied to another filesystem or restored from a backup is a new directory (a new identity), so it is unbaselined until its first session start; where `stat` gives no identity at all the record falls back to the path and a rename loses it. The key (`${SB_RUNTIME_STATE_DIR}/seal.key`, mode 0600) is readable by the same OS user as the hooks, so the following are deliberate, visible acts that this design documents rather than prevents: (1) reading the key and recomputing the record or a seal; (2) running a sanctioned writer yourself: `session-start`, `record-skill.sh` or the file-tool PostToolUse of `dev-cycle-check.sh` with a forged payload re-records whatever the files are at that moment, because the writers cannot tell who called them (a forged session start also prunes registry lines by the cap and, by the twin rule, the old-name line and marker of a renamed root: `mv P P.o`, a forged session start from `P.o`, then `cp -a P.o P` without the contract files leaves `P` ungated, because the record followed the identity to `P.o`); (3) removing BOTH path anchors of a root (its `baselined-roots` line and its `root-*` marker; for a rename also the record, which holds the identity) by a means the hooks cannot see, such as an interpreter one-liner, and then swapping or moving the contract files; a registry line or marker left keeps the path anchored, also after a copy, symlink or new directory is put at it, and a fresh session in another workspace does not change that, while the record alone does not hold a swapped copy; on a filesystem without birth time a reused `device:inode` anchors an unrelated directory (the accepted false positive above), not the reverse; or deleting the key together with the project's record pair (record and counter; the state seal alone is not enough, it only empties the state), which returns the install to the never-had-a-key state described above, and putting the key back afterwards; (4) the counter files are the only rollback witness and they are ordinary files: lowering the counter that survives (to 1 is enough) lets an older record that was recorded with the key be put back; (5) `roadmap-freshness.sh` is a hygiene gate: it stops a phase `SUMMARY.md` being committed with an unticked `ROADMAP.md` (it fails closed when `ROADMAP.md` is missing or the contract files moved away), but an agent that edits the roadmap and the summary together is not stopped; (6) edits to ordinary source files made through obfuscated shell code do not touch the artifact set (they can skip the floor for one edit, not turn it off) and are backstopped by the commit and stop gates; (7) the tool-consent keys (`.recommended_tools`, the tier) are kept by the hooks themselves and are not in the record; they cannot raise the tier above what the host probes, and docs/PROTECTED-READS.md lists every such read as class X with its reason; (8) `scripts/deploy-gate-snippet.sh` is a snippet pasted into a user's own deploy script and reads the config itself; it is outside the hook layer. A change by the user (an editor, `git checkout`, `git pull`) of a protected file looks the same as an agent's: the gate reports `ENFORCEMENT CONTRACT CHANGED` with the artifact, and the recovery is to revert the file or restart the session so that session start records it. Without openssl and python3 the record is a plain checksum, logged as a warning, and refused where either exists or a key exists.

| Stage | Requires | Blocks until |
|-------|----------|--------------|
| A — Planning floor | `required_planning` skills in state | SB pre-execution gates complete |
| B — Implementation window | Planning floor complete | Source edits are allowed; review/verify/ship remain final-delivery gates |
| C — Review recorded | `silver-review` in state | Source edits still allowed; finalization remains gated |
| D — Finalization | All `required_deploy` skills plus expected SB artifacts | Final delivery commands allowed |

The same hook also hard-blocks edits under the host plugin cache (`${SB_RUNTIME_HOME_ROOT}/plugins/cache/`) and direct writes to SB state files.

## Two-Tier Model

Silver Bullet enforces two **distinct** tiers:

| Tier | Trigger | Hook | Requires |
|------|---------|------|----------|
| **Planning floor** | Commands that create commits or push: `git commit`, `merge`, `cherry-pick`, `revert`, `am`, `rebase`, `fast-import`, `pull .` (a local merge, however the repository is spelled: `.`, `./`, `.git`, `$PWD`, `file://`), forced branch moves (`branch -f`/`-M`), a branch moved onto a stash commit (`checkout -B`/`switch -C`/`reset`/`branch NAME` with `stash`, `stash@{N}` or `refs/stash` as the start point: the agent's stashed work lands on the branch without a `git commit`), `subtree add|merge|pull`, plumbing (`write-tree`, `commit-tree`, `hash-object -w`, `update-ref` of `refs/heads/*` or `HEAD`), `git push`, `subtree push`, `http-push`, `send-pack`. Plain `git pull`, `git stash` and `git checkout -B`/`switch -C` to an ordinary start point create no commits of the agent's own and are not gated | `completion-audit.sh` | `required_planning` skills in state |
| **Planning floor** | Task-complete declaration (Stop/SubagentStop) | `stop-check.sh` | `required_planning` skills in state |
| **Final delivery** | `gh pr create`/`new`, `gh pr merge`, `gh release create`/`new`, `gh api` writes to pulls, merges, releases, git refs or contents, `hub pull-request`/`merge`/`release`, `glab`/`tea`/`az repos` PR and release verbs, raw `curl`/`wget`/`http` writes to the GitHub API, and deploys: deploy tools (`kubectl apply`, `helm upgrade`, `terraform apply`, `npm publish`, `docker push`, `fly deploy`...) and tasks, scripts (also those inside a `deploy/` directory) or workflows named deploy, release or publish, and `ssh`/`scp`/`rsync` as a deploy user | `completion-audit.sh` | All `required_deploy` skills + expected artifacts; for `gh release create` also `required_release` and the release gates below |

**How commands are classified.** `hooks/lib/tool-input/shell_analysis.py` parses the whole command like bash does and follows it in execution order: every line and every segment of `;`, `&&`, `||` and `|` chains, `$(...)`, backticks, here-documents fed to a shell, `sh -c` and `eval` code, wrappers (`env`, `command`, `nohup`, `timeout`, `xargs`, `find -exec`...), git global options (`-C`, `-c`, `--git-dir`) and git and gh aliases. Variables, arrays, positional parameters (`shift`, `"${@:2}"`) and the common parameter operators (`:-`, `#`, `%`, `/`, `:N`, `^^`...) are evaluated on literal values. A command with several verbs gets the highest tier (`git push && gh pr create` is final delivery). Commands that only mention a verb (`echo deploy`, `grep "gh pr create" docs/`, `kubectl get deploy`, `tldr git commit`) are not gated.

*Commands hidden behind a program the analyzer does not model.* A program without a handler (`taskset`, `uv run`, `poetry run`, `tmux`, `pwsh -c`, `parallel`, `vim -c`, `docker exec`, `kubectl exec --`, `ssh host 'cmd'`...) cannot hide a delivery verb that is written out in its arguments: every argument suffix that starts at a program word (`git`, `gh`, `make`, `kubectl`, a shell...) and every argument that reads as a command line is judged, and git settings and variables that hold a command line (`core.pager`, `diff.external`, `core.sshCommand`, `GIT_EXTERNAL_DIFF`, `difftool -x`, `bisect run`, `submodule foreach`, `grep -O`...) are walked. What they could do is reported as a possible action; arguments after a pattern option (`pytest -k "git commit"`) and the topic of `man`/`tldr` are not commands.

*Unseen code.* Code the analysis cannot read is held at the strictest tier instead of being waved through (the pseudo action `unseen`, completion tier). That covers a program word computed in the command itself: a variable assigned from `$(...)`, `read` or `mapfile`, an element of such an array, a parameter operator that cannot be evaluated, a positional parameter taken from such text, or xargs input handed to `git`/`gh`; `eval` of anything but a well-known environment tool (`eval "$(ssh-agent -s)"`, `eval "$(brew shellenv)"`, `eval $(poetry env activate)`, `source <(kubectl completion bash)`: the whole substitution must be that one tool with plain arguments); a shell or interpreter fed by a pipe from a command or by `<(...)` or an open descriptor (`bash /dev/fd/3`); `bash -s` without a readable script; inline interpreter code that runs a command which is not written out (`os.system(cmd)`, `"gi" + "t"`, `exec`, `base64`, `getattr`); `awk system(var)`; `sed e`; arithmetic, array subscripts, `${x:off:len}` offsets, `declare -i` assignments and `[[ -v name ]]` that evaluate a variable holding `$(...)`; a changed `IFS` whose value is unknown; git or gh aliases that cannot be resolved (config files, `GH_CONFIG_DIR` or `HOME` redirected, included or written in the same command, `gh extension install`); `gh api graphql` with an unreadable query; and syntax the parser rejects. A variable that is merely inherited from the environment (`$PYTHON -m pytest`, `$G commit -m x`) is not computed: it is judged by its arguments. A script below a computed directory (`"$(git rev-parse --show-toplevel)/scripts/check.sh"`) and a script fed from a literal file (`bash < setup.sh`, `cat setup.sh | bash`) are script files like `bash setup.sh`: their contents are not analysed, but they are not unseen code. When `completion-audit.sh` blocks on unseen code, `ca_unseen_reasons` (classify.sh) holds why.

*Bounded work.* The analyzer is bounded in cost, not only in steps. Input over 512 KiB is not parsed; the parser and the walker each stop after 1 s (the deadline is checked at every step), a stored value over 64 KiB or an array over 4096 items becomes unknown, brace sequences and `GIT_CONFIG_COUNT` are capped, and every regular expression applied to command text is linear. Going over a limit, or an analyzer fault, reports unseen code (strictest tier), so a crafted command is denied rather than timing the hook out; `dev-cycle-check.sh` starts the analyzer three times per Bash call, which still fits the 15 s hook limit. If python3 is installed but the helper does not finish, `classify.sh` holds the command at the strictest tier too. The analyzer needs `python3`; without it a regex fallback over every line catches the plain verbs and variable-built commands that name a delivery verb, and `sb_shell_analysis_helper_message` tells the agent how to proceed.

*Residual limits.* Script, makefile and sourced-file contents are opaque, not read (a script written and run in the same command is read from the text it was given; one whose written content cannot be read is unseen code); `parallel gh ::: 'pr create'`, `make SHELL=...`, `rg --pre`, `GIT_ASKPASS=/tmp/x.sh` and `core.hooksPath` run files whose contents are never read; an environment variable that was exported in a previous tool call is invisible. The agent has a shell as the same user, so these checks make a bypass deliberate and visible rather than impossible.

*Push scope residual limits (Invariant P).*

1. **Code git runs on its own.** Git hooks (`pre-commit`, `post-commit`, `pre-push`, `reference-transaction`, `post-checkout`), `core.hooksPath`, credential helpers, `core.sshCommand`/`GIT_SSH_COMMAND`, `remote.*.receivepack` (strict when set, but other configured programs are not judged) and `ext::` transports are not judged. An agent that writes a hook can push anything when an inert `git commit` runs; the corpus pins this as a residual row (a `post-commit` hook that runs `git symbolic-ref HEAD refs/heads/main`, then `git commit -m x && git push origin HEAD`: verdict intermediate, effect on main). Follow-up outside this package: gate writes to `.git/hooks/**` and `git config core.hooksPath|*.receivepack|credential.*`.
2. **Shell environment outside the command text, and ssh configuration.** The user-level `~/.ssh/config` and `/etc/ssh/ssh_config` (ProxyCommand, LocalCommand, KnownHostsCommand, XAuthLocation, PKCS11Provider, SecurityKeyProvider, Include, Match exec) are read by ssh, not by git, and are not judged. The host's shell snapshot (profile functions and aliases, for example a user `git` function), a `git` earlier on `PATH`, and variables exported in a previous tool call or through `CLAUDE_ENV_FILE` are not visible. Only the known redirecting variables in the hook's own environment are checked.
3. **Stale knowledge of the remote.** `refs/remotes/<remote>/HEAD` reflects the last fetch or `set-head`. A remote whose default branch was renamed since then, and which matches neither `main`, `master`, `init.defaultBranch` nor the stale target, is not recognised. The same holds when the remote's URL was changed after the last fetch (`git remote set-url`, a new `url.*.insteadOf`) by an earlier, separate command: `refs/remotes/<remote>/HEAD` still describes the old repository.
4. **Time of check versus time of use.** Background jobs started by earlier tool calls (`run_in_background`) can change HEAD or config between the hook and the push.
5. **Server-side automation.** Repository rules or workflows that merge or deploy on a feature-branch push are outside the gate.
6. **MCP.** The target repository is trusted to be the one named by the local remote URL. GitHub Enterprise hosts are always strict.
7. **gh placeholders.** `{owner}`/`{repo}` resolve to gh's base repository. In a fork checkout this may be `upstream`, while the release commit is read from `origin`.
8. **Strict-by-design false positives,** each with an actionable message. They cost an honest user one split command: `git fetch`/`pull`/`rebase`, test runners or `make` in the same command as the push; `git push origin "$(git branch --show-current)"`; `cd ~/...`; a forced push to an unqualified `src:dst`; `git push` retried in one command; a checkout without `refs/remotes/<remote>/HEAD` (the remedy is `git remote set-head <remote> --auto` once).
9. **Behaviour worth knowing.** A `gh` command with an alias or extension name that is not a built-in and not in the readable gh configuration is not classified as a delivery (residual); `gh api graphql` with `-F query=@file` or `--input` is treated as possible delivery, and `-f query=@file` is the literal text `@file` in gh, not a file. A leading variable assignment in the push command is accepted only from a fixed list with literal values: `RTK_DISABLED=1`, `NO_COLOR=1`, `CI=1`, `GIT_TERMINAL_PROMPT=0`, `LANG=<literal>`, `LC_ALL=<literal>`. Any other assignment (`GIT_DIR`, `GIT_CONFIG_*`, `GIT_SSH_COMMAND`, `PATH`, `HOME`, a value with `$` or a backtick, `+=`, arrays) is final delivery; the block message names it. `gh release edit` and `gh release upload` are not release creations the commit reader understands and deny as `cannot determine release commit`. `GH_REPO`/`GH_HOST` anywhere in a release command (or `GH_REPO` in the hook environment naming another repository) deny. An MCP push when the python3 helper is unavailable is final delivery (its target cannot be read). With `project.push_to_default_branch_tier: "intermediate"` the verdict is ignored, but the three read-only git calls still run (classification happens before the config is read).

`stop-check.sh` blocks **only** on the `required_planning` floor — it does **not** require the full `required_deploy` list. This is intentional (v0.30.0 #85): an agent may legitimately end a session mid-implementation as long as the planning floor is recorded. The full `required_deploy` list is enforced by `completion-audit.sh` when an actual delivery command runs. Intermediate commits and pushes need only the planning floor, so execution subagents can commit atomically mid-execution. **Invariant P (push).** A shell push is intermediate only when Silver Bullet can prove, from the command text and from read-only local git answers (`rev-parse`, `config -z --list`, `for-each-ref`; no network, no hooks run), that the command runs exactly one `git push` from one known directory, contains nothing else that could change the facts the proof relies on, and, under the git configuration in force, updates only `refs/heads/<B>` on one named remote, where every `<B>` is a spelled-out branch name that is not that remote's default branch. Anything not proved is final delivery. The accepted shape is `git push [-u] [<remote>] [<branch>|HEAD|<src>:<dst>]` as its own command, optionally after `cd <literal dir> &&` or `git checkout -b <new> &&` / `git switch -c <new> &&` in an unbroken `&&` chain, next to nothing but inert commands. The inert list is audited line by line: a git subcommand is inert only when every option is on its exact allowlist (no abbreviations; git accepts `--outp=` for `--output=`, which writes any file): `status` (`-s -b --short --branch --porcelain --long -v -z` and clusters of those), `add` (`-A -u -v -f -N --dry-run`), `commit` (`-a -q -v -s -n --amend --allow-empty --no-edit --no-verify`, `-m`/`-F` with a value; hooks run on commit, residual 1), `log`/`show`/`diff`/`shortlog` (display flags, `--format=`/`--pretty=`/`--max-count=`...; no `--output`, `-O`, `--ext-diff`, `--textconv`; they are refused when the stored configuration names a pager, an external diff driver or a textconv filter), `rev-parse`, `ls-files`, `describe` (no write options exist), `symbolic-ref [--short] [-q] HEAD` (read forms only), `config --get|--get-all|--get-regexp KEY|--list` (read forms only), `branch` with listing flags only, `remote`/`remote -v`/`remote get-url NAME`. The programs `echo`, `printf` (only without any dash-word: `printf -v NAME` and `-vNAME` assign a shell variable), `true`, `:`, `cat`, `head`, `tail`, `grep`, `wc`, `sleep`, `pwd`, `ls`, `test` and `[` have no option that writes a file (only a redirection does, and every redirection target must be `/dev/null`, `/dev/stdout`, `/dev/stderr` or `/dev/tty`). Every word of a top-level command (and every redirect target and heredoc body) must be a plain literal, a plain `$NAME`/`${NAME}` read or a command substitution whose commands are themselves inert: an expansion that assigns or computes in the current shell (`$((HOME=0))`, `$[X=1]`, `${X:=v}`, `${X=v}`, `${X:+v}`, `${!X}`, array forms, `$?`, process substitution) can change a variable git reads, so it makes the push final delivery (command substitutions run in a subshell, so their assignments do not persist). The cloud-session variables `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` are parsed: a malformed count or a missing key or value is final delivery, as is a key that changes what a push sends or runs a program (`remote.*.push|pushurl|mirror`, `push.*`, `alias.*`, `include*`, `core.hooksPath|sshCommand|editor|pager|fsmonitor`, `filter.*`, `diff.*`, `gpg.*`, `branch.*.remote`, `url.*.pushInsteadOf`); credential, `url.*.insteadOf`, `safe.directory`, `http.*` and `user.*` pass. For a `git commit` without a message on the command line the effective editor (`GIT_EDITOR`, then `core.editor`, then `VISUAL`, then `EDITOR`, git's own order) must be benign (`true`, `:`, `cat`) or unset; the gpg program settings (`gpg.program`, `gpg.*.program`, `gpg.ssh.defaultKeyCommand`) matter only for a commit when `commit.gpgsign` is on (status, add and the viewers never sign); the stock git-lfs filter commands (`git-lfs clean|smudge [--skip] -- %f`, `git-lfs filter-process [--skip]`) are not treated as programs. Every command inside a substitution (any nesting: inside a substitution, a heredoc, an assignment, a redirect target) is judged by the same inert rule and every write the analysis sees must go to `/dev/null`-type paths; the push corpus has rows S1-S34 that run such substitutions for real (writes to `.git/HEAD`, a planted pre-push hook, cp/mv/install/tee/sed -i, git checkout/switch/config/branch -f/reset/symbolic-ref/update-ref). Programs the push itself starts are final delivery unless stock: `core.sshCommand`/`GIT_SSH_COMMAND` must be a plain `ssh [-i KEY] [-p N] [-o Name=value]` line (no `-F`, ProxyCommand, LocalCommand, Include, provider options), credential helpers must be stock (`store`, `cache`, `osxkeychain`, `manager`, `libsecret`, `netrc`, `!gh auth git-credential`), `core.askPass`/`GIT_ASKPASS`/`SSH_ASKPASS`, `core.gitProxy`/`GIT_PROXY_COMMAND`, `core.alternateRefsCommand`, `uploadpack.packObjectsHook`, `GIT_SSH` and `GIT_EXTERNAL_DIFF` must be unset, `protocol.ext.allow` must be `never`, a remote URL or `url.*.insteadOf` must not name a remote helper (`ext::`, `<helper>::`, a scheme other than https/http/ssh/git/file), and `PATH` must have only absolute entries. `core.fsmonitor` as a boolean selects git's built-in monitor and is accepted. Mechanisms that make git or ssh WRITE a file at a path the setting names are final delivery too (they are the `--output=` class): `trace2.eventTarget|normalTarget|perfTarget`, `GIT_TRACE*` and `GIT_TRACE2*` with anything but a stream (`0`-`9`, `true`/`false`; a path or `af_unix:` socket is refused), `http.saveCookies` (with `http.cookieFile`), `fsmonitor.socketDir`, `gc.repackFilterTo`, `lfs.storage`, `GIT_LFS_PROGRESS`, `GIT_SHALLOW_FILE`, credential helpers with a `--file` or `--socket` option (`cache` takes `--timeout` only), and ssh options other than `StrictHostKeyChecking`, `BatchMode`, `ConnectTimeout`, `IdentitiesOnly`, `ServerAliveInterval`, `ServerAliveCountMax`, `Compression` and `ForwardAgent=no` (no `UserKnownHostsFile`, `ControlPath`, forwards, `-E`, `-D`, `-L`). A remote that is a local path, a `file://` URL, a bundle or `.` (also through `url.<base>.insteadOf` rewriting a hosted URL into a path) is final delivery as a deliberate rule: `git push` would run the receiving repository's own configuration and hooks (core.hooksPath, gc.recentObjectsHook, receive.procReceiveRefs, post-receive, updateInstead) on this machine, and the hook cannot read that configuration; honest feature pushes go to a hosted remote (https, ssh, git or scp-like). Credential helpers: only `store` (no `--file`), `cache` (`--timeout` only), `osxkeychain`, `libsecret`, `wincred`, `!gh auth git-credential` and git's own `git-credential-*` pass; Git Credential Manager (`manager`, `manager-core`) is steered to files by its own settings (trace, plaintext store, socket) and passes only when the consent file pins it (`{"trusted_programs": {"credential": [{"helper": "manager", "path": "/usr/bin/git-credential-manager", ...pin fields as for signers}]}}`, and the pinned file must be the one git finds on PATH). Remote URLs on a loopback host (`localhost`, `127.x`, `::1`, also over ssh or http) reach a repository on this machine and are treated like local paths; `[user@]host:/abs/path` is an scp-like hosted address. `GIT_TRACE*` may be `0`, `1`, `2`, `true` or `false` (stderr or off); 3-9 is a file descriptor and anything else a file, so both are refused; `SSLKEYLOGFILE`, `GIT_SSL_KEYLOGFILE` and `GIT_TEST_*` set in the hook's environment are refused (a variable exported only in the shell that runs the push is invisible, residual 2). Pagers are accepted only as the bare names `cat`, `less`, `more` or `most` with plain options, never by path. The pin of a trusted signer is checked when the hook runs; a file swapped between that check and the real run is a time-of-check-to-time-of-use residual. Shell builtins that change shell state are never inert, so they make the push final delivery: `read`, `export`, `declare`, `typeset`, `local`, `let`, `set`, `unset`, `eval`, `source`, `.`, `alias`, `unalias`, `exec`, `trap`, `builtin`, `command`, `pushd`, `popd`, `mapfile`, `shopt`, `umask`, `wait`, `cd -`/`cd ~`/`cd $X` (only a literal `cd DIR` at the start of an `&&` chain is modelled); and so are assignments outside the fixed list and `printf -v`. Stored settings that make an inert git subcommand run a program make the push final delivery: `core.fsmonitor` (a boolean selects the built-in monitor; whitespace is not stripped, so ` true` is a program path), `core.hooksPath` (also for the push itself: it names the pre-push hook), `gc.recentObjectsHook` (auto gc runs after a commit), `filter.*.clean|smudge|process` (the stock git-lfs commands, with or without `--skip`, are accepted, but `lfs.extension.*`, `lfs.customtransfer.*` and `lfs.standalonetransferagent` run programs and are not), and, for every command that renders a diff (log, show, diff, `status -v`, `commit -v`, a commit without a message when `commit.verbose` is on), `diff.external` and `diff.*.command|textconv`; the viewers also need a stock pager (`core.pager`, `pager.*`, `GIT_PAGER`, `PAGER` must be empty, `cat`, `less`, `more` or `most` with plain options). The signing and verification programs (`gpg.program`, `gpg.<fmt>.program`, `gpg.ssh.defaultKeyCommand`) matter for a commit when `commit.gpgsign` is on and for `git log`/`git show` (they verify signatures: `log.showSignature`, `%G?`/`%GS`/`%GK`, `--show-signature`), and `push.gpgSign` other than false makes the push itself sign. Booleans are read as git reads them (any non-zero integer, `1k`, `0x1`, `-1` are true; an empty value is false). A signing program is accepted only as a stock system signer: an absolute path to `gpg`, `gpg2`, `gpgsm` or `ssh-keygen`, a regular file owned by root that nobody else can write, outside the project and HOME; a signer anywhere else (for example a script in `/tmp`, as in the Claude cloud container, where `commit.gpgsign=true` and `gpg.ssh.program=/tmp/code-sign` make `git commit ... && git push` in one command final delivery, while the commit and the push alone are allowed) stays final delivery. `git commit --no-gpg-sign` as a real option (not a message, file name or pathspec; abbreviations are not accepted) never calls the signer and is accepted; plain `git log`/`git show` verify signatures, so with that config they are final delivery too. The user can bless a signer knowingly with an entry in the per-user consent file, never in the committed project config: print the entry with `python3 hooks/lib/tool-input/push_scope.py --trust-entry /tmp/code-sign` and add it to `{"trusted_programs": {"signing": [ENTRY]}}` in `${XDG_CONFIG_HOME:-~/.config}/silver-bullet/consent.json` (a regular file owned by you, mode 0600). The entry pins four things, the path, its real path, owner and mode, and the sha256 of the file content; the program is trusted only while all four still match, so a changed or replaced file denies. `/tmp` is world-writable: the entry still trusts whatever the pinned file is, so bless a file only when you know its content and who can replace it. Without it, honest `git commit ... && git push` in one command is final delivery in this container (split it into two commands). A hook script inside the hooks directory is residual 1. A single `bash -c`/`sh -c`/`bash -lc '<literal script>'` (the Codex shape) is judged by its script. A `cd` whose argument contains `..` is refused when a symbolic link is involved (bash's `cd` is logical, the proof is physical). The directory is the payload's `cwd` (Codex: `workdir` joined to it), never the hook's own working directory. The strict causes are: any other command on the line (`git checkout`, `fetch`, `config`, `stash`, `rebase`, `sh -c`, `eval`, test runners, `make`, function calls, assignments, background jobs, compound commands), `git -c` and `--git-dir`, git-redirecting variables in the environment (`GIT_DIR`, `GIT_CONFIG_*`, `BASH_FUNC_*`...), push options other than the plain boolean ones (long options must be spelled in full; `--mir` is not `--mirror`), tags, `--all`/`--mirror`/`--delete`, globs and deletions, a forced push to an unqualified destination, a destination that is a default branch (`main`, `master`, `init.defaultBranch`, the target of `refs/remotes/<remote>/HEAD`, compared case-insensitively), a push to a URL or path instead of a configured remote, git settings that change what a push sends (`remote.<name>.push|pushurl|mirror|receivepack`, `push.default` other than `simple`/`current`, `push.followTags`, `push.pushOption`, `url.*.pushInsteadOf`), a detached HEAD, a git that does not answer in time, and a checkout that does not know its remote's default branch (`refs/remotes/<remote>/HEAD` missing: run `git remote set-head <remote> --auto` once, which needs the network). The block message names the cause and the accepted shape. `project.push_to_default_branch_tier: "intermediate"` is the explicit opt-out.

**Invariant M (MCP write).** An MCP write (`push_files`, `create_or_update_file`, `delete_file`, `create_commit`, `create_branch`) is intermediate only when `owner` and `repo` are plain strings that match, ignoring case, a GitHub remote (`https://github.com/O/R`, `git@github.com:O/R`, `ssh://git@github.com/O/R`, `git://github.com/O/R`) of the checkout in the payload's `cwd`; that remote's default branch is known locally (`refs/remotes/<remote>/HEAD`); and `branch` is a spelled-out branch name (one leading `refs/heads/` is stripped) that is not `main`, `master`, `init.defaultBranch` or the target of that remote's `HEAD`. A missing branch (the repository default), a repository the checkout has no remote for, a GitHub Enterprise host, a `repository: "o/r"` shape, `create_tag`, `create_ref`, `update_ref` and `update_pull_request_branch` are final delivery. `hooks/core-rules.md` and `silver-bullet.md` describe the same split — keep all three in sync.

In the `devops-cycle` workflow the `_devops` variants (`required_planning_devops`, `required_deploy_devops`, `required_release_devops`) apply.

### Stop-gate details

- **Empty state.** An empty state file normally means a non-dev session and Stop is allowed. It is *not* allowed when the agent itself wrote project source this session. `trivial-file-clear.sh` (PostToolUse on Write, Edit, MultiEdit, NotebookEdit, apply_patch, Bash, exec_command and MCP tools whose name says they write) appends what each call wrote to the hook-only `files-written.<session start>` trace of the state directory (`hooks/lib/agent-writes.sh`): one entry per line, from the paths the shell analysis lists, resolved against the payload's cwd. Appends are single writes and a live trace is never rewritten, so concurrent hooks never lose an entry; the first record of a session removes the regular files of earlier sessions' traces; a trace holds 500 entries, then one `*` and nothing more. Stop applies the planning floor when the trace holds a write that can be under the project's source (`src_pattern` / `src_exclude_pattern`, tests excluded, the semantics the other gates use) and a still-dirty path is source. **Counted:** a file under source; a target that is the project root or a directory above it (`find . -exec sed -i`, `git checkout -- .`, `cp -r x .`, `rsync x/ .`); a glob inside the project, or above it when its components can match the project's own path (`/tmp/*.log` cannot lead to `/tmp/x/proj`; `*/*.js` and `/tmp/**/*.js` can) or that expands into source; a tree extract (`tar -x`, `bsdtar -x`, `unzip`, `patch`, `git apply`); and every write whose target cannot be known: an unreadable payload or command, python3 missing, a first path component that is an unresolved `$VAR` or `$(cmd)`, xargs input, an unresolved cwd, a path with an unresolved part under the project or above it, a variable command word (`"$BASH" -c '...'`, `${SHELL} -c`), `eval` of computed text, a dynamic script path or git subcommand, a program fed to a shell or interpreter on stdin (`| bash -v`, `| sh -h`, `python3 -v < prog.py`: `-v`/`-h` are not info flags there), inline interpreter code (`python3 -c`, `node -e`/`-p`, `perl -e`, `php -r`, `ruby -e`, `lua -e`, a program read from stdin, a dynamic or executing `sed`/`awk` program; even `python3 -c 'print(1)'` counts, the analysis cannot show it read-only), a glob that can name the state directory (`rm ~/.c*/.s*/files-written*`, `rm ~/.c*/.s*/session-start-time`, `rm -rf ~/.c*`), a session start that is missing or not a number (the trace is then `files-written.unknown`, a trace of any session counts, and nothing is rotated away), a file tool without a path, more than 500 distinct targets, and a trace that is a symlink, directory or FIFO (never followed or opened). A file tool's path is literal (`*` and `?` are part of the name). Local MCP write tools (a plugin-provided server is remote only when its own name is a known remote service) are read with the same path-key list as the PreToolUse write guard (`hooks/lib/tool-path-fields.sh`). **Not counted:** an interpreter or shell asked only for its version or help with nothing fed to it (`node --version`, `python3 -V`, `bash --version`; per program: shells take only `--version`/`--help`), HTTP and GitHub API reads (`curl`, `gh api`), `sed -f` / `awk -f` program files, files outside the project and outside its ancestors (`/tmp`, `~`, the state directory, another repository by absolute path), docs and other non-source paths, a notebook's cell text, MCP calls that name no path and every path of a remote service's MCP tools (GitHub, GitLab, Google, Slack, Notion, Linear, Figma and the like: not local files), and read-only commands (a pipeline or chain of allowlisted read-only programs with only `/dev/null` and `2>&1` redirects never starts the analysis). **Residual (writes that leave no trace):** a plain script, module or project-task run names no write, so `python3 script.py`, `./run.sh`, `make`, `npm test`, `npm run format` count only for the paths the analysis names; `bun -e`, `deno eval` and `deno run -` are not recognised interpreters (inline code there leaves no entry); the shared analysis has no writer entry for `cpio -i`, `7z x`, `iconv -o`, `git read-tree -u`, `git checkout-index`, `git clone` into a source directory, GNU `parallel`, formatters and build tools (`prettier --write`, `eslint --fix`, `black`, `gofmt -w`, `cargo fmt`), or any other program that writes without a redirect, so they leave an empty trace; an MCP write tool whose name does not match the hook matcher is not traced; and the PreToolUse state-tamper guard (G2) allows a glob spelling of the state directory (`rm ~/.c*/.s*/files-written*`); the trace records it as an unknown write, so Stop still applies the floor, but the guard itself does not refuse it, and a script file or interpreter that rewrites the state directory is outside the guard. So a chat-only session over the user's own pending edits stays allowed, also when the agent writes a scratch file outside source (`git diff > /tmp/x`, `tee ~/log`, a docs edit).
- **Loop breaker.** A block the agent cannot clear from inside the session (the branch file belongs to the host's global runtime state, so a branch switch or a concurrent session trips it) blocks once; when the host reports `stop_hook_active` the mismatch is released with an audit line in `stop-loop-release.log` and the planning floor is then evaluated against the skills recorded so far (a missing required skill still blocks, with the mismatch note). To start clean, `/clear` or start a new session so session-start re-scopes the state.
- **Stall flag.** The autonomous stall flag (100 tool calls without a recorded skill) lifts as soon as a skill is recorded after it.
- **Per-prompt gates.** The outcome checklist and instruction ledger belong to the parent's prompt: they hold the parent's Stop, never an ordinary subagent's SubagentStop. The checklist is derived from recorded skills and plan files and is sealed with a sha256 sidecar; a change or deletion made outside the hooks resets it to pending (`outcomes-tamper.log`; a hook-written `outcomes-seeded` marker proves a deleted checklist existed even when there is no ledger). Checklist and ledger files are per session (`outcomes-session-<session_id>.json`, `instruction-ledger-<session_id>.json`); without a session id the global file is used. A queue clear for a new goal needs the same provenance as an override and is audited. Ledger items keep per-item ids, survive a branch switch in the same worktree, and are resolved with the resolver's absolute path shown in the block.
- **Completion audit.** Every Task worker return sets a pending marker that only a `/sb:completion-audit` run *after* it clears (Skill call, a `silver-bullet invoke-skill` call that exited 0 and left a fresh adapter receipt, or the user's own command); an older audit line in the state file does not cover a later worker.
- **E2E harness marker.** The Stop exemption for the enterprise E2E routing row needs `SB_E2E_ENTERPRISE_MATRIX=1` in the hook's own environment and a marker file holding a future expiry epoch written by the harness; a `touch`-created file is ignored.

### Orchestrator Worker SubagentStop

In orchestrator parent mode, the parent session spawns Task **workers**, each executing one atomic flow. Stop/SubagentStop handling differs by role:

- **Worker (`SB_ORCHESTRATOR_WORKER=1`) on `SubagentStop`:** `stop-check.sh` clears the worker marker and exits 0. Workers are **not** individually subjected to the planning-floor or delivery gates — they perform a single flow and return to the parent. Enforcement is the parent's responsibility.
- **Parent on `Stop` with a pending flow queue:** `stop-check.sh` blocks and instructs the parent to spawn the next Task worker for the next flow before ending the session. The parent cannot declare the composition complete while flows remain queued.

This division means the planning-floor and delivery gates are enforced **once, at the parent level**, against the cumulative state the workers contributed — never redundantly on each worker SubagentStop.

## CI Status Gate

`ci-status-check.sh` reads the latest GitHub Actions run for the current branch (`gh run list`); without `gh` it exits quietly.

| Event | Commands | When CI failed or was cancelled |
|-------|----------|---------------------------------|
| PreToolUse | `git push`, `gh pr create`, `gh pr merge`, `gh release create` | Denied |
| PostToolUse | `git commit` | Warning only (the commit already happened; blocking would deadlock CI fixes) |
| PostToolUse | `git push`, `gh pr create/merge`, `gh release create` | Block message |

The status checked is the latest run of each workflow on the newest commit of the branch (a red workflow is not hidden by a later green one). A `git push` is let through only when every changed file is under `.github/workflows/` or `tests/` (or is `package.json`); a commit-message convention no longer waives a red CI. A human can waive the block for 30 minutes (`SB_CI_OVERRIDE_TTL_MINUTES`) with the flag file `${SB_RUNTIME_HOME_ROOT}/.silver-bullet/ci-red-override`; an expired flag is removed. When `gh` is missing, fails or exceeds its timeout (`SB_GH_TIMEOUT_SECONDS`, default 8) the hook says CI status could not be checked. `state.trivial_file` in the project config is honoured only as the state directory's own `trivial` file. Runs that are in progress are informational. Deploy commands are not checked by this hook; `completion-audit.sh` separately requires the release commit to be green before `gh release create`.

## Release Gates

On `gh release create`, `completion-audit.sh` adds the release gates the project config enables (`release.require_*`; all `false` in the template, `true` in this repository). The commit checked for green CI is the one `gh release create` will release: an existing tag's commit, else `--target` (resolved against the remote branch), else the remote default branch, else `HEAD`. The tag and target are read the way gh reads them (`hooks/lib/tool-input/release_scope.py`): `gh release create`/`new`, `gh api repos/{owner}/{repo}/releases` (flags and fields in every spelling, `-f`/`-F`/`--field`/`--raw-field`, clusters such as `-if`, `-p` as the preview flag, no prefix abbreviations) and the MCP `create_release`, in the repository of this checkout (`{owner}`/`{repo}` or the slug of `remote.origin.url`), with one release per command. A second release, a repeated or computed `tag_name`/`target_commitish`, a body read from `--input` or `-F @file`, `GH_REPO`/`GH_HOST`, another tool (`hub`, `glab`, `curl`...) or an unknown flag blocks with `cannot determine release commit` and the reason. Validators and the RC predicate are loaded from the plugin, never from the project tree; a missing or non-executable plugin validator blocks the release:

- **Plugin runtime matrix** (`require_plugin_runtime_matrix`) — matching `matrix=` markers from `scripts/run-release-live-matrix.sh`, `tests/e2e-live/run-e2e-live-tests.sh` and the enterprise inline journey in the runtime state dir.
- **Pre-release quality gate** (`require_pre_release_quality_gate`) — the markers `adversarial-review-clean`, `sentinel-skills-clean`, `quality-gate-stage-3` and `full-test-suite-rerun` in the quality-gate state file, plus the plugin's `scripts/validate-launch-review.sh` and `scripts/validate-sentinel-skills-manifest.sh`, run against the project's files.
- **RC validation matrix** (`require_rc_matrix`) — six operator-local `status=pass` markers written by `scripts/run-rc-validation-matrix.sh` at the commit being released. A `--dry-run` (`status=dry-run`), a skipped cell, or a marker for another commit does not count; skips are accepted only for one commit when a human writes `commit=<sha>` into `rc-validation/skip-waiver`.
- **Green CI** on the release commit (always).

The stages behind these markers, and the order to run them in, are described in [RELEASE.md](RELEASE.md). The quality-gate state file is cleared on session start, so markers cannot carry over from an earlier session. The full-suite rerun runs through `verify-tests`, which also writes `${SB_RUNTIME_HOME_ROOT}/.silver-bullet/verify-tests-state` so final delivery can detect stale source changes.

## Bypass Detection

Silver Bullet detects and blocks:
- Out-of-order skill invocation (finalization before review)
- State file tampering (direct writes to state files are blocked by `dev-cycle-check.sh`; `session-start` validates paths)
- Hook skip attempts (hooks fire on every tool call, not just session start)
- Trivial-mode abuse (agents cannot create the legacy trivial marker — `trivial-file-guard.sh` — and `session-start` deletes stale markers)

The audited escape hatch for orchestrator directives is a user message whose first line is `SB OVERRIDE: <reason>` (12+ character reason of at least two words; only a parent session's own prompt event counts: host `session_id` required, never a worker/delegate or `agent_id` payload; a `transcript_path`, when the host sends one, must be a regular file under the host runtime root once symlinks are resolved; while a Task worker marker is fresh the prompt must also come from the session recorded as the parent and carry the host's `transcript_path`, so on a host that sends none the override is refused until the marker is deleted or lapses after 2 hours, otherwise the refusal names the marker and the file to delete if the subagent was interrupted). The hook writes a hash-chained record to `.planning/orchestrator-override-log.jsonl` before it clears the pending directive and the flow queue; if the record cannot be written nothing is cleared. The override message is itself a prompt: when it reads as work it seeds its own outcome checklist (route, plan, verify), so the override releases the orchestrator's hold on Stop but not that checklist. It does not lift parent-mode tool restrictions or other PreToolUse gates.
