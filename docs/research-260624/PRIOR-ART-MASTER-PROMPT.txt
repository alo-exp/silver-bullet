## 1. Executive Framing — What Silver Bullet Built

**Silver Bullet (SB)** is an open-source **Agentic Process Orchestrator (APO)** for software engineering and DevOps. It is **not** merely an agent that can call tools. Its product model is a **declarative, machine-readable catalog** (`docs/apo-catalog.json`) that defines:

| Level | Description | Example |
|-------|-------------|---------|
| **Process** | A team's end-to-end delivery system | `PROC-SB-SE-DEVOPS` — default SE + DevOps process |
| **Workflow** | Named path inside a process (pre-composed, reusable component, or dynamic route) | `WF-SILVER-FEATURE`, `WF-REVIEW-TRIAD`, `WF-SILVER-ROUTER` |
| **Atomic flow (`AF-*`)** | Minimal non-redundant capability unit — one subagent work package each | `AF-PLAN`, `AF-EXECUTE`, `AF-VERIFY`, `AF-BLAST-RADIUS` (~27 canonical flows) |
| **Flow step / skill** | Reusable instruction implementing a step inside one or more atomic flows | `silver-plan`, `silver-verify`, artifact reviewers |

### Core differentiators (search for equivalents)

1. **Hierarchical dynamic composition** — Pre-composed workflows are **defaults**, not mandatory ceremony. At runtime the orchestrator may **prune, insert, or substitute** atomic flows when catalog metadata and context prove a leaner or safer tree — every deviation is **audited** in a `composition_log` with catalog-backed rationale.

2. **One atomic flow = one subagent work package** — Workflows are **dependency DAGs** of atomic flows. Independent flows run in **parallel** (host-native multitask); dependent flows **join on V-gates**. Parent orchestrator **schedules and verifies only**; workers implement.

3. **V-model verification at every level** — Inspired by systems-engineering V-model and SEI "many short V's":
   - Each **atomic flow** has a V-loop: input/need → work product → verification (building it right) → validation (building the right thing) → repair loop → escalation → evidence.
   - Each **flow step** has its own per-step V-loop that **rolls up** before the parent flow V-gate may pass.
   - Composed workflows have **V-loop rollups** plus a final **user-intent validation gate** (material claims from the original prompt checked against artifacts/evidence).

4. **Hook-enforced skill chains** — Runtime hooks block commits, PR creation, deploy, and session stop unless required lifecycle skills have been recorded. Config is authoritative (`templates/silver-bullet.config.json.default`); hooks fail closed on substantive delivery actions.

5. **Evidence tiers and opted-in tool governance** — Once a team opts into tools (Graphify, agentmemory, Alumnium, etc.), they become **mandatory when relevant** to the active atomic flow; tool outputs are **V-model evidence** with sufficiency classes, staleness rules, and failure policies (warn / repair / block / degrade).

6. **No-redundancy invariant** — No duplicate capability classes at atomic-flow, workflow, skill, or docs/runtime level. Catalog is **sole source of truth**; markdown matrices and site pages are **generated or validated views**.

7. **Team process packs** — Teams customize processes (add/remove/reorder workflows, mandate gates) **without forking** atomic flow definitions.

8. **SE + DevOps unified catalog** — Same APO model covers feature delivery (`silver:feature`), UI (`silver:ui`), bugfix, research, release, incident, deploy, canary, blast-radius, DevOps routing, etc.

### Execution architecture

- **Parent orchestrator** (`silver-orchestrator`): reads `orchestrator-directive.json`, spawns **Task workers** from per-flow templates (`.silver-bullet/orchestrator-workers/<TEMPLATE>.md`), advances queue via hooks. Parent **never implements inline**.
- **Composer skills** (`silver:feature`, `silver:devops`, …): queue builders referencing catalog `workflow.composition_tree` — not inline procedure.
- **Composition patterns supported:** sequence, conditional branch, parallel join, repair loop, compensation/rollback, workflow-as-component reuse, dynamic prune/insert/substitute.

### What SB explicitly is NOT looking to duplicate

- Generic "LLM agent with tools" demos
- Unstructured prompt chains with no catalog or gates
- "Agent says done" without inspectable evidence
- Hand-maintained workflow prose disconnected from machine-readable contracts
